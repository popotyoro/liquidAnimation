# 将来対応リスト

今後検討する機能を記録する。実装時期と優先順位は未定。

## 注がずに液体が溜まるパターン

- [ ] 上から注ぐ水流を表示せず、画面の下から自然に液体が溜まっていく表現を追加する。
- [ ] 指定した液量まで水位が上がり、穏やかな揺れを残して落ち着くようにする。

主な用途は、1画面内の`List`に並ぶ複数の行Viewへ、それぞれ液体が溜まるアニメーションを適用すること。

実装はSwiftUIの通常のアニメーションを第一候補とする。各行に既存の物理モデル・`MTKView`・更新ループを持たせる方式は避け、投入率`0...1`に応じた塗りの高さを補間する。現在の注水とは別の軽量なmodifierとして作り、配色など必要な部分だけを共有する。

- [ ] まず水位の上昇だけを実装し、複数行を同時に動かしたときの表示と負荷を確認する。
- [ ] 必要に応じて小さな水面の波を加え、溜まり終わったら動きを止める。常時更新は前提にしない。
- [ ] 行の安定したIDと再生状態を対応させ、スクロールによる再表示で意図せず最初から再生されないようにする。

溜まる速さや再生のきっかけ、画面外の行の扱い、パターンの選択方法は実装時に検討する。

## Haptic Feedback（触覚フィードバック）

- [ ] 液体のアニメーションに合わせた触覚フィードバックを追加する。

振動を発生させるタイミング、強さ、オン・オフ設定は、実装前に検討する。

## 端末のシェイクに液体を連動させる

端末を振ったとき、その方向や強さに合わせて液面が揺れるようにする。

- [ ] 端末の動きを取得し、画面内の左右方向の加速度を液体の動きへ反映する。
- [ ] 振る強さに応じて波を起こし、振り終えたら徐々に静まるようにする。
- [ ] 連動のオン・オフと感度を設定できるようにする。
- [ ] 一時停止中・バックグラウンド中の扱いと、実機での操作感・負荷を確認する。

センサーの細かな揺れは平滑化し、入力に上限を設けて数値計算の不安定化を防ぐ。指定した液量を維持し、満水近くで振った場合の上端の扱いも検討する。端末を傾けたままの液面変化まで対応するかは、シェイクへの連動とは別に決める。

## 粒子方式で扱っていた表現を再導入する

今回の簡略化で省いた表現を、将来の対応候補として残す。以前の試作では、粒子を個別に動かし、複雑な液体形状を扱っていた。ただし、玉状の見た目や過剰な跳ね返り、水位誤差があり、完成した液体表現には至っていなかった。

- [x] 着水時に水面から飛び出す飛沫を表現する（重力で落下し、水面に再吸収する小規模な飛沫）。
- [ ] 水流から分離した水滴が重力で落ち、たまった水へ戻る動きを表現する（注ぎ終わりの細い末尾のみ試作。注水中の分裂は未対応）。
- [ ] 水面が盛り上がるだけでなく、巻き返る・砕けるなどの複雑な形状を扱う（着水点の両側から外へ広がり、低くなって戻る輪郭を試作中。巻き返り・砕波は未対応）。
- [ ] 液体内部の局所的な流れや渦を含む、2Dの流体計算を再検討する。

現在の「指定量で止まる」「平均水位が指定量に合う」「注水後に静まる」を維持すること。独立した水滴や飛沫も総量に含め、玉が跳ね続ける挙動に戻さない。現在の水面計算に小規模な飛沫を組み合わせた。水流にも描画上のうねりと太さの変化、終了間際の水滴への分離を追加した。注水中の分裂や巻き返りは未対応。全面的な流体計算が必要かは表現と負荷を比較して判断する。

## リアルさを最優先する表現パターンを試す

現在の軽量な表現と比較するため、液体のリアルさにこだわったパターンを一度試作する。YAGNIの方針で表現を一つずつ追加し、実装・検証・ユーザーの確認を区切りに進める。最初は既存の水滴処理を再利用した「注ぎ終わりの細い水流の分離」を試す。ソルバーの置き換え、比較用UI、設定項目の追加は必要になった段階で検討する。

- [ ] 分離した水滴の着水波を再検討する（保留）。小さな波の試作は注水の余韻と見分けづらかったため取り下げた。再開する場合は、見た目への効果を先に確認する。

- [ ] 現在の方式を残し、リアルさを優先した試作と切り替えて比較できるようにする。
- [ ] 水流の分裂・水滴の合流、着水時の巻き返り・砕波、内部の渦を扱える流体モデルを検討する。
- [ ] 透明感、反射・屈折、厚みによる色の変化、泡や飛沫の細かさを含めて質感を作り込む。
- [ ] 同じ注水条件で画像・動画と実機の処理時間・メモリ・発熱を比較する。

この試作では、まず表現の到達点を確認する。60fpsを下回る場合も結果と条件を記録し、通常版の性能目標とは分けて評価する。GPUによる物理計算や背景を参照する屈折も候補とするが、方式は未定。指定量の管理は維持し、本採用や通常版への置き換えは試作を見て判断する。

## 気泡と着水点の質感

- [x] 着水点から巻き込まれ、揺れながら浮上する少量の気泡を追加する。
- [x] 気泡を透明な中心・縁・反射光で描き、水面や寿命で消す。
- [x] 水面の傾きと着水点周辺の明暗で、単調な塗りを和らげる。
- [x] ビールの水面に残り、徐々に薄くなる泡の層を試作する。
- [ ] 気泡の合体・分裂が必要か検討する。

気泡と水中模様は描画を補う近似であり、空気と水の相互作用や内部の渦は未計算。気泡は最大128個とし、水量の保存や既存の飛沫の挙動へ影響させない。実機での60fpsと発熱は別途確認する。

## 液体の種類を選ぶ

水・ビール・炭酸水・粘度のある水の4プリセットと、種類とは独立した色の選択を実装した。ビールの表面に残る泡の層も試作した。より厳密な粘性表現などを小さく試す。

| 候補 | 表現したい特徴 |
| --- | --- |
| 水 | 透明感、軽い流れ、飛沫。現在の表現を基準にする |
| ビール | 琥珀色、上昇する気泡、水面にたまる泡の層 |
| 炭酸水 | 細かな気泡が溜まった後も上がる。溶存ガスの減少は未対応 |
| 粘りのある液体（蜂蜜など） | 太くつながる水流、ゆっくり広がる動き、飛沫の少なさ |

- [x] 設定画面で水・ビール・炭酸水・粘度のある水を選択する。
- [x] 種類の標準色と、ブルー・アンバー・グリーン・ピンクを選択する。
- [x] 粘度のある水の波・飛沫・水流のうねりを、現在のモデル内で控えめにする。
- [x] ビール・炭酸水は注水終了後も上昇する気泡を発生させる。
- [ ] 粘度・光沢・気泡などの細かなパラメーターを調整するUIを検討する。
- [ ] 溶存ガスの減少に合わせて、炭酸の気泡が少なくなる表現を検討する。
- [ ] 現在の減衰による近似に加え、粘性応力・付着・糸引きを扱えるモデルを検討する。
- [x] ビールの泡に含まれる液体を着水済み量の内数で管理し、排液後も指定量を維持する。
- [ ] 泡による液面の押し上げや溢流が必要か検討する。

色や光沢は主にMetal、流れや粘度はSwift側の物理モデルで扱う。蜂蜜のような高粘度の流れや、壁へ付着して残る表現には、現在の浅水モデルで対応できる範囲を見極める。種類を変えても指定量の管理を維持し、60fpsへの影響を実機で確認する。

## 数値計算ライブラリの活用

以下の3候補を記録する。いずれも流体シミュレーション一式を提供するものではなく、計算の実装・高速化を補助する。現時点では追加していない。

| 候補 | 提供形態・用途 | このプロジェクトでの検討内容 |
| --- | --- | --- |
| [MLX Swift](https://github.com/ml-explore/mlx-swift) | SPM対応。多次元配列の演算、CPU/GPU実行。iOS対応 | 2D格子へ拡張する際に、近傍セルの更新や圧力の反復計算を試作する候補。流体方程式・境界条件・水量保存は別途実装する。 |
| [Swift Numerics](https://github.com/apple/swift-numerics) | SPM対応。複素数や汎用的な数値型・数学関数 | 必要な数学処理が増えた場合の補助。現在の浅水モデルを置き換えたり、GPUへ移したりするものではない。 |
| [Accelerate](https://developer.apple.com/documentation/accelerate) | OS標準フレームワーク。SPM追加は不要。CPUでの配列・行列演算を高速化 | `vDSP`・`vForce` による配列演算や数学関数の一括処理を検討する。現在の128列程度で効果が出るかは実測する。 |

MLXはAppleの機械学習研究チームが開発するOSSで、GitHubの公開組織は `ml-explore`。[Apple公式のOpen Sourceサイト](https://opensource.apple.com/projects/mlx/)にも掲載されている。Appleは[WWDC26の数値計算セッション](https://developer.apple.com/videos/play/wwdc2026/328/)で、MLX Swiftによる2D格子の熱分布計算などを紹介している。流体への適用は、このプロジェクトでの検討案である。

- [ ] 2D流体計算を試す段階で、MLX Swiftと直接Metalで計算する方式の実装量・負荷を比較する。
- [ ] CPU計算がボトルネックになった場合、Accelerateを使う箇所を計測結果から選ぶ。
- [ ] 複素数や汎用数値型が必要になった場合、Swift Numericsの採用を検討する。

採用前に、実機でフレーム時間・CPU/GPU時間・メモリ使用量を比較する。追加するだけで高速化・高品質化すると判断せず、指定量で止まること、水量保存、注水後の減衰、Swift 6の並行性チェックを維持する。
