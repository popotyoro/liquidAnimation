# テストの設計と実行

2026-10-24のテスト整理で採用した基準。本体の計算・描画・操作の振る舞いは変更しない。

## 仕様を読めるケースにする

`@Test`の表示名は、日本語で条件と期待結果を書く。関数名は`lowerCamelCase`とする。「画像を出力する」「メソッドを呼べる」だけでは仕様の検証にしない。液量保存と波の減衰、一時停止と再開など、失敗理由の異なる振る舞いは別のケースにする。同じ仕様の境界値や液体の種類はパラメーター化する。

一つのケースで確認するのは一つの論理的な結果であり、`#expect`を一つに制限する意味ではない。例えば「一時停止で状態が変わらない」は、水位・液量・泡の複数の値で確認する。前提が満たされないと検証できない場合は`#require`で失敗させ、`if`で検証を飛ばさない。

## Four Phase Test

1. **準備**：そのケース専用の設定・モデル・描画資源と期待値を用意する。必要な初期状態まで進める処理もここに含める。
2. **実行**：対象の操作を実行する。時間変化の仕様では、経過中の観測値を集める。
3. **検証**：観測できる結果を仕様と比較する。実行ループ中の検証を散在させず、失敗した仕様が分かるようにする。
4. **後始末**：各ケースが所有する値・参照・GPU資源を解放する。現在はスコープ終了とARCで完結し、Metal描画はGPUの完了を待ってから戻る。外部状態を変更していないケースに空の`tearDown`は追加しない。

private関数の呼び出し回数や分割構造を固定しない。SwiftとMetalで共有する型のメモリ配置は、描画経路が依存するABIの仕様なので明示的に検証する。

## 並行実行で干渉させない

Swift Testingの既定の並列化を使い、`.serialized`は付けない。各ケース・各引数がモデル、操作状態、描画バッファ、コマンドキュー、描画先を所有する。アプリの`UIApplication`・Scene・キーウィンドウは取得・変更しない。固定ファイル名への画像出力もしない。

PNGや計測レポートはメモリから`Attachment.record`で現在のテストへ添付する。テスト同士で出力先を共有せず、テスト中に共有ディレクトリを作成・削除しない。カレンダーの日付・ロケール・タイムゾーンは固定し、アニメーションの形状は進行率を指定して検証する。実時間の待機で特定のフレームを狙わない。

`@MainActor`が必要なモデル・描画テストはその隔離を保つ。テストタスクの並行実行と、MainActor上の処理を複数CPUで同時に実行することは別である。速度を上げるために本体の隔離やSwift 6のチェックを弱めない。

### SuiteのMainActor隔離を外せる範囲

`LiquidFillShapeTests`は`nonisolated`な形状とローカルな`Path`の計算だけを扱うため、Suiteの`@MainActor`を外した。MCPでテストビルドと対象テストの成功を確認した。

その他は、テスト対象の隔離を確認して判断する。

| 対象 | 現在の判断 |
| --- | --- |
| 水面モデル・プリセット・入力・再生・操作状態のSuite | 本体の`WaterModel`・`FluidPlayback`・`FluidControls`がMainActor隔離されているため維持する。 |
| SwiftUIの描画・Metal描画・転送計測のSuite | UI描画器またはMainActor隔離された`FluidSimulation`を使うため維持する。 |
| 軽量版の配色テスト | `Color.liquidFill(for:)`がアプリの既定のMainActor隔離を受ける。テストだけの注釈除去はコンパイルエラーになることを確認した。 |
| 粒子メッシュのテスト | 純粋な座標変換だが、本体の生成器と`WaterModel.Bubble`・`Drop`がMainActor隔離されている。独立した値型として明示的に`nonisolated`・`Sendable`にする余地があるが、今回の調査では本体を変更していない。 |

Suiteの注釈を各メソッドへ移したり、処理全体を`MainActor.run`で包んだりしても、その処理の並列化にはならない。物理計算を複数CPUで同時に検証する場合は、UIから独立した数値計算部分とMainActor上の管理部分を分離する設計を別途検討する。現在のプロジェクト方針では、水面モデルと描画バッファの変更をMainActor内に保つ。

## 描画と実行の確認範囲

自動検証では、本番の`.liquidFill`、日付セル、波の形状、操作バー、Metalの転送・合成経路を使用する。塗られる領域、進行率による面積の変化、水面の凹凸と静止、計測値の変更、透明度などを画素または出力値で検証する。画像の寸法が正というだけでは表示確認を済ませない。

Sceneへの接続が必要な`NavigationStack`・`TabView`の画面全体、実際のキーフレーム再生、タッチ・VoiceOver・「視差効果を減らす」の端末設定は、この並列ユニットテストだけでは確認できない。画面全体の確認は通常起動で別途行う。今回、共有ウィンドウを使う画像採取ケースを並列ユニットテストから外したため、これらを自動検証済みとは扱わない。

ビルド・実行・テストは[AGENTS.md](../AGENTS.md)に従ってXcode MCPを使い、iPhone 18 Proを選ぶ。MCPが返す`.xcresult`には画像とレポートが添付される。性能レポートは合否の速度基準ではなく、計測条件をそろえて比較するための資料である。

2026-10-24の整理後、MCPで全229件が成功。スキームの`parallelizable="YES"`を維持し、テスト内に`.serialized`の指定がないことを確認した。セル・波・拡大文字の計測表示の添付画像も目視確認した。
